Benchmark report · LAN video delivery

Push beats poll: Redis Streams + WebSocket vs HLS and DASH on a local network

One encoder, three delivery systems, identical bytes. We measured how fast each gets a viewer to the first frame, how close to real time they play, how quickly each new segment reaches the viewer, and what happens under load and packet loss.

1Summary

On a LAN, the bottleneck in live streaming is not bandwidth, it's discovery: how a player finds out a new segment exists. HLS and DASH players poll a playlist or compute availability from a clock; our system (LANFLIX) pushes each segment down an open WebSocket the moment Redis has it.

That shows up exactly where you'd expect. New segments reach our viewers a median of after they exist, versus for HLS and for DASH. Our first frame appears in (HLS , DASH ), and viewers play behind real time (HLS with defaults, tuned).

It is not a clean sweep, and this report says so. Seeking is where we lose: median against for HLS. Both are imperceptible, but the cause is a real design flaw: after a seek we push everything up to the live edge, which also wastes bandwidth. HLS and DASH also win on everything the open internet needs: adaptive bitrate, CDN caching, native iPhone playback. And the benchmark exposed three bugs in our server, fixed before these numbers were taken (§8).

2Setup

A single ffmpeg process encodes a looping 720p30 test source in real time (H.264 High, 2 s GOP with keyframes only on segment boundaries, AAC 128 kb/s) and tees the encoded packets to all three systems at once. Every system receives bit-identical frames at the same instant, so every difference measured below is delivery, not encoding.

Five configurations were measured. HLS and DASH each ran twice: with the players' defaults, and tuned to the most aggressive standard (non-low-latency) setting, so our results are compared against the best these protocols can do without LL-HLS/LL-DASH.

Each configuration ran trials in headless Edge (Chromium), interleaved round-robin so drift in machine load can't favor any one system, each in a fresh browser profile. A trial joins at the live edge, plays 15 s, then seeks to four pseudo-random points in the stream history (the same points for every system in a given trial). Frame timing comes from requestVideoFrameCallback, which reports when a frame was actually presented on screen, not merely decoded. Client and origin share one machine and one clock, so per-segment delays are measured directly rather than estimated.

3Latency

3.1Time to first frame

From telling the player to start at the live edge until its first frame is on screen. Ours needs one round trip: the socket opens and the newest segment arrives with the init segment. hls.js fetches a playlist, then an init segment, then media; dash.js fetches and parses an MPD first.

3.2Delay behind real time

Glass-to-glass: for every frame presented during steady playback, the time since the encoder produced it. HLS's default holds three segments back (about 6 s) for safety; its tuned setting and ours both start one segment behind. What's left over after that is delivery.

3.3New-segment delivery: push versus poll

The purest measure of the architecture: once a new segment exists at the origin, how long until the viewer has its bytes? Ours is pushed the moment Redis stores it. An HLS player only notices after its next playlist refresh; a DASH player requests on a schedule computed from the manifest's clock.

3.4Seeking inside the stream history

The one latency measure we lose. All three are well under the ~100 ms where a seek starts to feel slow, but ours is measurably slower, and it gets slower with each successive seek in a session (median for seeks 1–4, while HLS stays flat). Two causes, both ours to fix: the server reads a page of four segments (~2.4 MB) from Redis before sending the first, and, because a seek pushes everything up to the live edge (§4.2), the next seek's segment queues behind megabytes still in flight. An earlier version was worse still: it read the entire history before sending anything (§8).

4Cost

4.1Requests to the origin

Polling has a price paid by the server, per viewer, forever: every HLS viewer re-fetches the playlist every couple of seconds even when nothing changed. Ours opens one socket per session; seeks and position reports ride on it.

4.2Segments fetched per session

The flip side, and a real weakness: after a seek, our server pushes every segment from the seek point up to the live edge, while hls.js stops at a 30-second buffer. A session that seeks far back pulls far more data than it will watch. The fix is flow control (the client asks for the next window as it plays), not yet built.

5Scaling to many viewers

N concurrent viewers join our origin at the live edge; for each new segment we record when every viewer received it, and SHA-256-check every byte against what was published. The load generator and the server share one 8-core machine and loopback, so this measures our software, not a network.

The first run found a real flaw. Each viewer held its own blocking Redis read, each tying up a connection from a pool of 80; past 80 viewers the rest queued, and Redis sat at 81 blocked clients. We replaced it with a fan-out hub: one Redis tail per movie, broadcast in-process to every viewer. Redis work now scales with the number of streams, not viewers.

Integrity: across every load step, of expected segment deliveries arrived, with hash mismatches.

6Packet loss

This project began as a comparison with raw UDP streaming, the multicast-style approach that sends each packet once to everyone. We streamed the same clip as MPEG-TS over UDP through a receiver that drops a controlled share of datagrams, then counted what no longer decodes.

Read this section carefully. It does not show ours beating HLS or DASH on loss. All three run over TCP, which retransmits: on a lossy link their bytes still arrive intact, just later. The comparison here is TCP delivery versus UDP delivery, and we did not inject loss into the TCP systems (the test host has no kernel-level loss emulator). What we did verify is that our delivery is byte-exact: every segment in the load test matched its published SHA-256.

8What the benchmark fixed

Running the benchmark before writing it up changed the product. Each of these was found by a measurement, fixed, and re-measured; the numbers above are from the fixed code.

  • Seek read the whole history first. A seek loaded every segment from the target to the live edge out of Redis before sending byte one (about 24 MB for 40 segments). Now paged and sent as it is read. That removed the worst case, but seeks are still slower than HLS for the reasons in §3.4.
  • Redis connections per viewer. Every viewer held a blocking read; the connection pool capped at 80. Replaced with a per-movie fan-out hub: Redis blocked connections at 200 viewers went from 81 to 2 (one per movie, plus the benchmark origin's own), and server CPU from 31% to 12% of a core.
  • Hardcoded codec string. The player declared H.264 level 3.0 for every stream; 720p is 3.1 and 1080p is 4.x, and Chrome merely tolerated it. It now reads the real profile and level, and whether audio exists, from the stream's init segment.

Earlier in the same session, testing with real 8–10 minute uploads also caught encoding freezing after about 8 minutes (ffmpeg's progress output silently filled a pipe), fixed with a regression test that reproduces it.

9Limitations

  • One machine, loopback. Client, server and origin share a host, so absolute times are optimistic for a real Wi-Fi network (which adds a few ms and jitter to every system alike). Relative ordering is what these results support.
  • Not tested against low-latency variants. LL-HLS (blocking playlist reload, partial segments) and LL-DASH (chunked CMAF) exist to attack exactly the polling delay measured in §3.3, and would narrow the gap considerably. We compared against standard HLS/DASH, tuned.
  • No loss on TCP. See §6: loss was only applied to UDP.
  • Synthetic source. A test pattern, 720p30, one bitrate. No adaptive bitrate was involved on any side.
  • Our origin is one process. No clustering or CDN; it serves a LAN, which is what it was built for.

10Reproducing

With Redis, Kafka and the server running (see the project README):

go build -o bench/bin/source.exe ./bench/source
go build -o bench/bin/load.exe  ./bench/load
go build -o bench/bin/udp.exe   ./bench/udp
bench/bin/source.exe -duration 5400 &          # one encoder → all three systems
node bench/run.js --trials 10 --sample 15 --seeks 4
bench/bin/load.exe -pid <server pid> -n 1,10,25,50,100,200
bench/bin/udp.exe
python bench/analyze.py                        # → bench/results/summary.json
