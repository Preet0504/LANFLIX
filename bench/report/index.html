Benchmark report · LAN video delivery

Push, poll or peer-to-peer: LANFLIX against HLS, LL-HLS, DASH and WebRTC on a local network

One encoder, eight delivery configurations, identical video. We measured how fast each gets a viewer to the first frame, how close to real time it plays, how quickly new media reaches the viewer, what seeking costs, and what happens under load and packet loss.

1Summary

LANFLIX pushes video chunks from Redis Streams down one WebSocket per viewer. We compared it with the protocols a LAN streaming app could use instead: classic HLS and DASH, which poll; Low-Latency HLS, which uses long-held HTTP requests; and WebRTC, which sends RTP packets and was built for calls.

WebRTC wins live latency by a wide margin: glass-to-glass, against for the best segment-based system. It cannot seek, rewind or resume, and a joining viewer waits for the next keyframe ( to first frame here).

At equal chunk sizes, LANFLIX and LL-HLS reach near parity on latency: against , with LL-HLS slightly ahead. Both get new media to the viewer in milliseconds, because hls.js requests each part before it exists and the origin holds the request open. LANFLIX gets there with one socket and reaches the first frame in (LL-HLS: ). LL-HLS spends about HTTP requests per viewer per minute.

At 2 s segments, push does not lower glass-to-glass latency. LANFLIX plays behind live against for tuned HLS; the per-trial ranges overlap. Latency is set by chunk size and hold-back, not by how discovery works. What push does win at 2 s is getting each new segment to the viewer in instead of , and a first frame in .

LANFLIX loses on seeking ( against for HLS) and on bandwidth: after a seek it pushes everything to the live edge, downloading about five times more media per session. Adding WebRTC and LL-HLS also exposed four bugs in the LANFLIX player and server, fixed before these numbers were taken (§8).

2Setup

A single ffmpeg process encodes a looping 720p30 test source in real time: H.264 High with no B-frames, a keyframe every 2 s, and AAC audio. It tees the encoded packets to every system at once, so every difference measured below is delivery, not encoding. There are no B-frames because WebRTC cannot carry them, and low-latency live encoders don't use them. WebRTC's audio is a second, Opus encode of the same source, because WebRTC cannot carry AAC.

Eight configurations were measured:

Each configuration ran trials in headless Edge (Chromium). Trials were interleaved round-robin so drift in machine load can't favor any one system, each in a fresh browser profile, after a seeded random 0–2 s wait. That wait matters. Without it, one round of sessions took an almost constant 146 s (exactly 73 segments), so every system joined at the same point of the segment cycle in every trial. An earlier run's latency ranking was an artifact of that.

A trial joins at the live edge, plays 15 s, then seeks to four pseudo-random points in the stream history (the same points for every system in a given trial). Frame timing comes from requestVideoFrameCallback, which reports when a frame was actually presented.

The encoder's clock comes from its RTP output, which leaves ffmpeg as soon as each frame is encoded: the 1st percentile of arrival minus timestamp over frames. A plain minimum was wrong, because at each loop of the source ffmpeg releases a few frames early. As a check, no 200 ms chunk becomes available before its last frame is encoded (1st percentile after).

3Latency

3.1Time to first frame

From telling the player to start at the live edge until its first frame is on screen. LANFLIX needs one round trip: the socket opens, and the init segment and newest chunk arrive together. hls.js fetches a playlist, then an init segment, then media; dash.js fetches and parses an MPD first.

WebRTC connects in , then waits for the next keyframe. A dedicated WebRTC encoder would send one on request; this shared encoder keeps its fixed 2 s schedule, so the result is pessimistic for WebRTC.

3.2Delay behind real time

Glass-to-glass: for every frame presented during steady playback, the time since the encoder produced it. Segment-based systems hold back at least one chunk plus a safety margin: default HLS holds three 2 s segments, and tuned HLS and LANFLIX hold one. The low-latency pair holds 0.6 s. WebRTC holds only its jitter buffer ( on average here).

3.3New-media delivery: push versus poll

Once a new chunk exists at the origin, how long until the viewer has its bytes? LANFLIX pushes each chunk the moment Redis stores it. A classic HLS player only notices after its next playlist refresh; a DASH player requests on a schedule computed from the manifest's clock.

LL-HLS closes this gap by requesting the next part in advance (a preload hint) and having the origin hold the request until the part exists. That is push built out of HTTP requests.

3.4Freezes

Gaps of more than 250 ms between presented frames during steady playback, measured from the frames themselves so the measure is identical for every player. Only dash.js froze regularly, and more often when tuned for low delay.

3.5Seeking inside the stream history

Seek latency is where LANFLIX loses. All of these are well under the ~100 ms where a seek starts to feel slow, but LANFLIX is about twice as slow as HLS: HLS fetches exactly the segment it needs, while LANFLIX restarts a Redis read and a stream. Median seeks 1–4 in a session: .

Before the seek-epoch fix (§8), seeks with 200 ms chunks took up to 11 s, stuck behind data pushed for the previous position.

4Cost

4.1Requests to the origin

Polling has a price paid by the server, per viewer, for as long as they watch. Every HLS viewer re-fetches the playlist every couple of seconds even when nothing has changed. LL-HLS triples that: a blocking playlist request plus a part request for every 200 ms of video. LANFLIX and WebRTC make one connection per session.

4.2Media downloaded per session

The flip side, and a real weakness. After a seek, LANFLIX's server pushes every chunk from the seek point to the live edge, while hls.js stops at about a 30-second buffer. A session that seeks far back pulls far more data than it will ever watch. The fix is flow control (the client grants the server credit as it plays), which is not built yet.

5Scaling to many viewers

N concurrent viewers join LANFLIX's origin at the live edge. For each new segment we record when every viewer received it, and SHA-256-check every byte against what was published. The load generator and the server share one 8-core machine and loopback, so this measures the software, not a network. This test predates the encoder change and the seek protocol; the live fan-out path it measures is unchanged apart from a per-write epoch check.

The first run found a real flaw. Each viewer held its own blocking Redis read, each tying up a connection from a pool of 80. Past 80 viewers the rest queued, and Redis sat at 81 blocked clients. We replaced it with a fan-out hub: one Redis tail per movie, broadcast in-process to every viewer. Redis work now scales with the number of streams, not viewers.

6Packet loss

This project began as a comparison with raw UDP streaming, the multicast-style approach that sends each packet once to everyone. We streamed the same clip as MPEG-TS over UDP through a receiver that drops a controlled share of datagrams, then counted what no longer decodes.

Read this section carefully. It compares raw UDP against protocols that recover from loss: TCP for LANFLIX, HLS and DASH, and retransmission plus a jitter buffer for WebRTC. We did not inject loss into any benchmarked system (the test host has no kernel-level loss emulator), so this does not rank those systems against each other under loss.

7Where each system wins

Measured results from this study, plus capabilities that follow from each protocol's design.

Which to use. For a live, interactive stream (a watch party with voice, a camera, a game), use WebRTC. For a LAN library that people rewind, resume, join late and scrub, LANFLIX's design fits: server-side resume, per-viewer analytics, one socket per viewer and the fastest startup, and in low-latency mode it matches LL-HLS on latency. For the internet, iPhones or CDNs, use HLS or LL-HLS.

8What the benchmark fixed

Running the benchmark before writing it up changed the product. Each of these was found by a measurement, fixed and re-measured; the numbers above are from the fixed code.

  • Viewers started up to 2 s behind the requested point. Chromium clamps a seek past the end of buffered media to that end. With one chunk per GOP the first chunk always covered the start point, which hid this. With 200 ms chunks the server starts at the preceding keyframe, and the player landed there instead. The player now applies a start or seek position once buffered media covers it.
  • Seeks stuck behind stale pushed data, up to 11 s. After a far-back seek, the previous position's backfill (thousands of 200 ms chunks) was still queued in the player and in flight on the socket. Fixed with seek epochs: the server drops writes from superseded streams and sends a seek_ack marker, and the player clears its queue and drops anything before it. There is a regression test.
  • A CPU-burning retry loop. Once pushed-ahead media filled the browser's buffer quota, the player "freed" an empty range, which retried the append at once: about 30,000 failed appends a second. It now evicts only what is actually behind the playhead, and otherwise waits.
  • A frozen forward seek. After a long backfill, a seek toward live was clamped (the first bug again) and playback never resumed. Fixed by the same change.
  • Earlier: seeks read the whole history before sending anything; each viewer held its own Redis connection, capped at 80 (now one per movie, and CPU at 200 viewers went from 31% to 12% of a core); the codec string was hard-coded to H.264 level 3.0; and encoding froze after about 8 minutes because ffmpeg's progress output filled a pipe (a regression test reproduces it).

The harness needed two fixes too: the encoder clock calibration (§2) and the randomized join timing (§2). Both changed results, and both runs affected were discarded.

9Limitations

  • One machine, loopback. Client, server and origin share a host, so absolute times are optimistic for a real Wi-Fi network, which adds delay and jitter to every system. WebRTC's jitter buffer in particular would grow.
  • No loss on the benchmarked systems. See §6: loss was only applied to raw UDP.
  • WebRTC's startup is pessimistic. The shared encoder can't send a keyframe on request, as a dedicated WebRTC sender would.
  • LANFLIX-LL is a benchmark configuration. The server, store and player handle 200 ms chunks, but the app's upload path still produces 2 s chunks.
  • Not tested: LL-DASH (chunked CMAF), and WebRTC with a player tuned for minimum jitter buffer.
  • Synthetic source. A test pattern, 720p30, one bitrate. No system used adaptive bitrate.

10Reproducing

With Redis, Kafka and the LANFLIX server running (see the project README):

go run ./bench/source &                        # one encoder → all eight configurations (:8095)
node bench/run.js --trials 10 --sample 15 --seeks 4
curl -s "localhost:8095/requests?since=0" > bench/results/requests.json
go run ./bench/load -pid <server pid> -n 1,10,25,50,100,200
go run ./bench/udp
python bench/analyze.py                        # → bench/results/summary.json
python bench/report/build.py                   # → this report
