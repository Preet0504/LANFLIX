# Chapter 7 — Storage: Redis and Redis Streams

The store is where the design's central idea lives: **a stream of video is an append-only log whose entry IDs are timestamps.** This chapter explains Redis from first principles, then shows how one data structure answers every question delivery needs to ask.

## 7.1 What Redis is

**Redis** is an in-memory data store. Every value lives in RAM, which is what makes it fast: a typical operation takes microseconds, and a single instance handles hundreds of thousands of operations per second. A few properties matter for design:

- **Data structures, not just values.** Besides plain strings, Redis offers hashes (field → value maps), sets, sorted sets (members ordered by a numeric score), lists, and **streams**. Each comes with commands that operate on it server-side, so you ask Redis "give me the 5 highest-scored members" rather than downloading everything and sorting.
- **Single-threaded command execution.** Commands run one at a time, so **every single command is atomic**. `HSETNX` ("set this field only if it doesn't exist") can never race with another `HSETNX` on the same field.
- **Transactions and pipelines.** A **pipeline** sends many commands in one network round trip. A **transaction** (`MULTI … EXEC`) additionally guarantees that the commands execute together, with nothing from another client in between.
- **Expiry (TTL).** Any key can be given a time to live, after which Redis deletes it automatically.
- **Persistence is optional.** Redis can snapshot to disk or log every write, or keep nothing. LANFLIX runs it with persistence **off** (`--save "" --appendonly no`). Fragments can be regenerated by re-encoding the uploaded file, and viewer positions are also recorded in Kafka. The cost is honest: restart Redis and live buffers, metadata and resume points are gone. For a LAN party appliance that's acceptable; for a product it wouldn't be, and turning persistence on is a one-line change.
- **Blocking reads.** Some commands can *wait* for data to arrive, which is the foundation of low-latency notification (§7.5).

## 7.2 Redis Streams in one page

A **Redis Stream** is an append-only log. Each **entry** has:

- an **ID** of the form `<milliseconds>-<sequence>`, e.g. `42000-22`. IDs must strictly increase: each new entry's ID is greater than the previous one.
- a small map of **fields**, e.g. `seq=21 pts_ms=42000 keyframe=1 data=<bytes>`.

The core commands:

| Command | Meaning |
|---|---|
| `XADD key <id> field value …` | Append an entry. |
| `XRANGE key <start> <end> COUNT n` | Read entries with IDs in [start, end], oldest first, at most n. `-` means the lowest ID, `+` the highest; prefixing an ID with `(` makes the bound exclusive. |
| `XREVRANGE key <end> <start> COUNT n` | The same, newest first. |
| `XREAD BLOCK 0 STREAMS key <id>` | Return entries after `<id>`; if there are none, **wait** until one is added. |
| `XADD … MINID ~ <id>` | While appending, drop entries with IDs below `<id>`. `~` means approximately, which is cheaper. |

Redis normally generates IDs from the wall clock, but any ID can be supplied, as long as it increases. **That's the trick LANFLIX is built on.**

## 7.3 The central idea: the ID *is* the timestamp

Every fragment is appended with the ID

```
<the fragment's timestamp in the video, in ms> - <fragment sequence number + 1>
```

For example, the fragment starting 42 seconds into the video, sequence 21, gets ID `42000-22`. (The `+1` exists because Redis reserves the ID `0-0`, and the very first fragment starts at 0 ms with sequence 0.)

Because IDs are ordered, and ordered by *video time*, the log becomes an index by time for free:

| Question the delivery server asks | Operation |
|---|---|
| Which fragment contains 1:05.3? | `XREVRANGE movie:<id> 65300 - COUNT 1`: the last entry starting at or before 65,300 ms |
| Give me everything from there onward | `XRANGE movie:<id> <that id> + COUNT 4`, repeated page by page |
| What's the newest fragment (the live edge)? | `XREVRANGE movie:<id> + - COUNT 1` |
| Tell me the moment a new fragment exists | `XREAD BLOCK 0 STREAMS movie:<id> <last id>` |
| Drop anything older than 3 hours | `XADD … MINID ~ <now_pts − 10,800,000>` |

A secondary index would have to be kept consistent with the data, and it would be one more thing to query and to get wrong. Here the primary key already sorts the data in the order every query needs.

> **Principle: choose identifiers that carry meaning your queries need.** A well-chosen key can make a secondary index unnecessary. Time-series databases, event stores and log-structured systems all use this idea: store in the order you'll read.

## 7.4 Seeking to a keyframe: a small secondary index

In standard mode every fragment starts with a keyframe, so "the fragment containing time T" is always a valid place to start decoding. In low-latency mode, only one fragment in ten starts with a keyframe. Starting a viewer anywhere else would hand the decoder frames that reference frames it never received.

So LANFLIX keeps a small **secondary index**: a Redis **sorted set** `movie:<id>:keyframes`, with one member per keyframe fragment. The member is the entry ID and the score is the timestamp. To start a viewer at time T:

```
ZREVRANGEBYSCORE movie:<id>:keyframes  T  -inf  LIMIT 0 1     →  "40000-21"
```

That's the last keyframe fragment at or before T. Delivery starts there, and the player skips forward to T once the media covering T is buffered (chapter 9).

A secondary index is only useful if it can never disagree with the data. The keyframe index is written **in the same transaction** as the fragment:

```
MULTI
  XADD  movie:<id>  40000-21  seq 20 pts_ms 40000 keyframe 1 data <...>   MINID ~ <cutoff>
  ZADD  movie:<id>:keyframes  40000  "40000-21"
  ZREMRANGEBYSCORE movie:<id>:keyframes  -inf  (<cutoff>
EXEC
```

Either all three happen or none do. No reader can see a fragment without its index entry, or an index entry pointing at a fragment that retention has already trimmed.

(For streams recorded before the index existed, the server falls back to the "containing entry" query, which is correct for standard mode, where every fragment is a keyframe. This keeps old data readable when a new structure is introduced.)

## 7.5 Following the live edge: blocking reads

A viewer at the live edge needs each new fragment *the moment* it's appended. Polling ("anything new?" every 100 ms) wastes work and adds up to 100 ms of delay. Instead, the reader issues:

```
XREAD BLOCK 0 COUNT 64 STREAMS movie:<id> 42000-22
```

Redis replies immediately if entries after `42000-22` exist. Otherwise it **holds the connection** and replies the instant `XADD` appends one. This is a **long poll** at the database layer, the same idea LL-HLS uses at the HTTP layer (chapter 4). The latency from append to reader is on the order of a millisecond.

Each blocked `XREAD` occupies one connection from the client's connection pool while it waits. With one blocked read per *viewer*, a pool of 80 connections supports 80 viewers before everyone else queues. That's why chapter 8's hub keeps one blocked read per *stream*.

## 7.6 Reading history in pages

When a viewer seeks back 40 minutes, the server must send 40 minutes of fragments, but not all at once and not all from memory. Backfill reads **pages** of 4 entries:

```
XRANGE movie:<id>  40000-21  +  COUNT 4      → entries a, b, c, d
XRANGE movie:<id>  (d        +  COUNT 4      → next four, starting just after d
...                                           until a page comes back short: the live edge
```

Sending starts after the first page, not after reading everything. Memory is bounded at four fragments. And the exclusive bound `(d` continues exactly after the last entry sent, with no duplicates and no gaps. Combined with flow control (chapter 8), the server reads further pages only as the viewer's window allows.

> **Principle: paginate by the last key seen, not by page number.** "Everything after key X" stays correct while the data grows. "Page 7" shifts when new entries arrive. This is called **keyset pagination** (or cursor pagination), and it's what well-designed APIs use.

## 7.7 Retention by time

Memory is finite (chapter 1: about 1.35 GB per hour per stream), so each stream keeps a **retention window**, 3 hours by default. Because IDs are timestamps, retention by *time* is one option on the append itself: `MINID ~ <pts − 3h>` drops everything older than 3 hours of video. Trimming by entry *count* would behave differently for different fragment sizes: 5,000 entries is 2.8 hours of 2 s fragments but only 17 minutes of 200 ms fragments. A time-based limit means the same thing in both modes.

The `~` (approximate) matters. Redis stores a stream as a tree of blocks of entries, and approximate trimming removes only whole blocks. That's cheap enough to do on every append, at the cost of keeping a few extra entries.

## 7.8 The rest of the keyspace

Everything else LANFLIX stores in Redis, and why each key has the type it has:

| Key | Type | Holds | Why this type |
|---|---|---|---|
| `movie:<id>` | Stream | The fragments | Ordered by time, blocking reads, time-based trimming |
| `movie:<id>:init` | String | The init segment | One blob, read once per viewer |
| `movie:<id>:keyframes` | Sorted set | Keyframe fragment IDs by time | "Largest score ≤ T" is one command |
| `movie:<id>:meta` | Hash | Title, room, status, start time, chunk duration | Several named fields, updated individually |
| `movie:<id>:alive` | String with 10 s TTL | Lease: still encoding? | Expiry does the failure detection (chapter 6) |
| `movies:all`, `rooms:all` | Set | IDs of every movie / room | Membership, no order needed |
| `room:<id>:meta` | Hash | Room name, creation time | Named fields |
| `rooms:byname` | Hash: normalized name → room ID | Unique room names | `HSETNX` claims a name atomically |
| `resume:<movie>:<client>` | String with 30-day TTL | A viewer's latest position | One value, overwritten; expires if unused |
| `client:<client>:movies` | Set | Streams a viewer has started | "Continue watching" list |
| `analytics:<movie>:reach` | Sorted set: client → furthest position | Audience retention | Range counts by score (§7.9) |

Two of these show general techniques worth calling out.

**Unique names with an atomic claim.** Two hosts typing "Movie Night" at the same moment must end up in the same room. LANFLIX normalizes the name (lowercase, whitespace collapsed) and then runs `HSETNX rooms:byname "movie night" <new-id>`. That sets the field only if it doesn't already exist, as a single atomic command. Exactly one caller wins and creates the room; everyone else reads the winner's ID and joins it. There's no lock and no race window. This **"claim with a conditional write"** pattern is how you make any create-if-absent operation safe under concurrency, in any database that has a conditional write.

**Monotonic updates with `ZADD GT`.** The analytics service records the furthest point each viewer reached with `ZADD analytics:<movie>:reach GT <position> <client>`. The `GT` option updates the score only if the new one is **greater**. Events can therefore arrive out of order, be replayed from the start of the Kafka topic, or be processed twice after a crash, and the result is always the same: the maximum. An operation you can safely apply again is called **idempotent**, and making consumers idempotent is the standard way to survive at-least-once event delivery (chapter 10).

## 7.9 Why Redis, and not something else?

| Alternative | How it would work | Why LANFLIX doesn't |
|---|---|---|
| **Files on disk + a manifest** (the HLS way) | Each fragment a file; a playlist lists them | Finding "the fragment containing T" means scanning the playlist; there's no built-in "notify me of new files", so readers poll |
| **A SQL database** | A table of fragments, indexed by (movie, pts) | Fine for random access, but no blocking read for new rows (you'd poll or bolt on a notification system), and large binary values are awkward in most SQL stores |
| **Kafka for the video bytes** | One topic per stream; offsets as positions | Kafka *is* a durable log, and can even look up offsets by timestamp. But it's built for high-throughput durable pipelines, not millisecond hand-off of each fragment to many independent readers; per-stream topics and retention are heavier to manage; and it's another thing that must be up for playback to work. Kafka is used where durability and replay matter: events (chapter 10). |
| **Just the server's memory** | A slice of fragments per stream in the Go process | The fastest option, but state dies with the process, can't be shared by several server instances, and duplicates what Redis already does well |

The deciding factor is that one Redis Stream serves **all four access patterns** delivery needs (seek by time, sequential read, live notification, time-based expiry) as native operations. When a data structure matches your access patterns that closely, the code around it becomes small and hard to get wrong.
